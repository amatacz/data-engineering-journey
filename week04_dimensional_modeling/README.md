## PODSUMOWANIE
### 1. Cel i zakres
Model przedstawia dane z NYC Yellow Taxi dataset pobrane z https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page
Zakres danych styczeń - kwiecień 2026 włącznie. 
Tabela staging.yellow trips zawiera 14 908 446 rekordów, rekordy odfiltrowane w finalnej tabeli dw.fact_trips 14 171 199 rekordów.

Schemat zawiera tabele:
* fact_trips -> tabela faktów zawierająca dane na temat przejazdów taksówką
* dim_date -> tabela wymiaru z informacjami na temat daty przejazdu
* dim_time -> wymiar zawierający godziny przejazdu
* dim_vendor -> wymiar ze szczegółami przewoźnika
* dim_payment_type -> wymiar z informacjami dotyczącymi płatności
* dim_location_scd2 -> wymiar z danymi na temat lokalizacji SCD2


### 2. Jak uruchomić
* Pobranie danych z przedziału 01.2026-04.2026: https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page
* Pobrać dane Taxi Zone Lookup Table CSV z https://d37ci6vzurychx.cloudfront.net/misc/taxi_zone_lookup.csv (podmień ściezkę w 05a)
* Załadować dane do Postgresa do schematu *public*
* Tworzenie modelu, uruchomić po kolei pliki SQL: 01 → 02 → 03 → 04 → 05a → 05b → 05c → 06 → 07
* Skrypty można uruchamiać ponownie, zapewniona została idempotencja.

### 3. Decyzje projektowe
1. Proces biznesowy:
  Realizacja kursu taksówką, rejestrowana przez system taksometru i raportowana do TLC.
2. Grain
  `fact_trips` -> jeden wiersz = jedna podróż taksówki, jeden rekord z pliku 'TLC Yellow Taxi'. Jest to najniższy poziom, rejestrowany jako jeden rekord bez względu na liczbę pasażerów.
3. Surrogate key
  Surrogate key w `dim_location` identyfikuje wiersz w bazie danych, a nie sam id lokacji w tym przypadku. Nie zmienia się, ale tez nie ma odzwierciedlenia w realnym świecie. W przypadku slowly changing dimensions, lokacja może zmienić swoje atrybuty, np. `service_zone`, więc surrogate key będzie wskazywało na konkretną wersję obowiązującą w dniu kursu.
4. Dlaczego rodzielamy `dim_date` i `dim_time` zamiast umieścić w jednej tabeli `dim_datetime`
  Ze względu na:
  * liczebność -> daty i czas liczone co do minuty daje ponad 500 tys. wierszy na rok, z każdym rokiem wzrost byłby znaczący.
  * dim_time -> 1440 wierszy, grain to minuty, nie sekundy, ponieważ byłoby to 86 400 wierszy, ponadto tak szczegółowe informacje na temat czasu nie są potrzebne do sensownej analizy
  * atrybuty w tabelach są od siebie niezależne -> np. `is_weekend`, `month_name` nie zależą od `dim_time`
  * analizy wykonywane są zależnie od jednego albo drugiego wymiaru -> *ile kursów rano, każdego dnia?* albo *czy ruch jest wiekszy w weekend?*

### 4. Decyzje implementacyjne
1. Model ma 2 warstwy -> staging i dw (data warehouse)
  Staging zawiera surowe dane: tabele "yellow_trips" oraz "taxi_zones_v1" i "taxi_zones_v2" (v2 potrzebne, do SCD2)
  DW zawiera zdenormalizowane tabele wymiarów (date, time, vendor, payment, location) i tabelę faktów (fact_trips)
2. Tabela uploadowana umieszczona w domyślnym schemacie *public* została zmigrowana do schematu *staging*, lepiej reprezentuje faktyczne umiejscowienie danych w procesie. Migracja wykonana przy użyciu komendy ALTER TABLE SET SCHEMA
3. Dim_date zawiera wiersze dla całego roku 2026, celem tego zabiegu jest elastyczność w doładowaniu danych dla pozostałych miesięcy roku dla dalszej analizy.
4. Wiersz techniczny z FK -1, świadczy o tym, że dane nie mogły być dopasowane do istniejących rekordów, gdy wartość jest NULL lub występuje kod spoza słownika. "Unknown" oznacza, że dana wartość została świadomie zaraportowana jako nieznana.
5. Klucze główne tabel generowane są automatycznie chyba, że konkretna wartość zostanie podana w zapytaniu. Dlatego właśnie użyta została składnia GENERATED BY DEFAULT, a nie GENERATED ALWAYS - always wymusza świadomą deklarację wartości poprzez OVERRIDING SYSTEM VALUE, dzięki czemu chroni przed przypadkowym wpisaniem klucza. Wybrałam GENERATED BY DEFAULT ponieważ wiedziałam, że będą istniały klucze, które będę wpisywać samodzielnie (-1), więc jest to wygoda, wymaga to jednak większej uwazności przy wprowadzaniu danych.
6. Zastosowano NULLS NOT DISTINCT, ponieważ domyślnie PostgreSQL traktuje każdy NULL jako unikatową wartość. NULLS NOT DISTINCT chroni przed wielokrotnym wprowadzeniem wierszy z brakującym kluczem naturalnym - chroni to przed wieloma przypadkowymi "Unknown"
7. Metody pozwalające na zachowanie idempotencji: 
  * Użycie klauzuli ON CONFLICT... DO UPDATE w wymiarach SCD1 aktualizuje wiersze, w których wystąpił konflikt wartościami podanymi w INSERT - czyli nie odrzuca ich.
  * WHERE NOT EXISTS w initial load SCD2 wstawia do pierwszej wersji tabeli tylko nowe wiersze, tylko te, których jeszcze nie było.
  * TRUNCATE w tabeli faktów zastosowane zostało, żeby uniknąć problemów z wielokrotnym ładowaniem tych samych danych. TRUNCATE tabeli faktów nie zablokuje żadnej innej tabeli. TRUNCATE tabeli wymiaru zablokowałoby wprowadzenie danych do faktów (zależność po FK)
8. Dane na temat przejazdów nie mają kluczy naturalnych, wprowadznie surrogate key *trip_key* pozwala na identyfikację przejazdów po ID (integer, nie jest potrzebny bardziej złożony klucz)

### 5. SCD2 w dim_location_scd2
* Konwencja wersjonowania: półotwarte przedziały, pierwsza wersja danych ma datę początkową 1900-01-01, aktualna wersja danych ma datę końcową ustaloną na 9999-12-31, obecnie obowiązujące wersje oznaczane są równiez flagą is_current
* Zasymulowano zmianę SCD2 używając do tego tabeli staging.taxi_zones_v2. Dla 3 lokalizacji zmieniono atrybut *service_zone* z Yellow -> Boro (wybrano 3 najniższe ID z service_zone = 'Yellow Zone'), dodano nową strefę z ID 900. Pozwala to na zasymulowanie zmiany atrybutów w tabeli wymiaru location wraz z zachowaniem historii tych zmian. Mała liczba zmienionych rekordów to symulacja, procesu - strefy TLC praktycznie się nie zmieniły.
* Data efektywna jako custom setting + SET LOCAL, zastosowanie tego mechanizmu pozwoliło na wprowadzenie daty, od której obowiązują nowe wersje zaktualizowanych atrybutów lokalizacji. A użycie zmiennej lokalnej umożliwiło wprowadznie tej daty 1 raz, zamiast wpisywanie jej w kilku miejscach (mniejsza podatność na błędy). Należy pamiętać, że data efektywna to data obowiązującej zmiany, a nie data wprowadzenia ich do systemu (data uruchomienia).
* W ramach jednej transakcji (użycje transakcji pozwala trzymać się zasad ACID i zapewnia brak lokalizacji zamkniętych - is_current=False - ale bez nowszej wersji) najpierw zamykamy wybrane wersje (zmiana *is_current* na **false** oraz *valid_to* na **datę efektywną**), a następnie wprowadznie nowych wersji z datą *valid_from* z **datą efektywną** oraz flagą *is_current* jako **true**. Krok drugi - wprowadzenie nowej wersji, może zostać wykonany tylko po kroku 1 - zamknięcie wersji.
* Zastosowanie partial unique index pozwala zagwarantować jedną aktualną wersję dla ID -> ID może występować kilka razy, ale tylko 1 wiersz z danym ID może mieć is_current = true
* Wstawiając dane do tabeli faktów, łącząc staging.yellow_trips z dim_location poza łączeniem po ID lokalizacji, używany też jest warunek filtrujący po dacie rozpoczęcia trasy - pozwala to na dołączenie danych lokalizacji obowiązujących w momencie wykonania przejazdu. Unikamy przypadkowego wielokrotnego załadowania danych.
* Potwierdzeniem efektywnej zmiany atrybutów 3 lokalizacji jest wynik poniższego zapytania
```
select dls.location_id, 
	case when dd.full_date < '2026-02-01' then 'before feb 1st' else 'from feb 1st' end as period, 
	dls.service_zone
from dw.fact_trips ft 
join dw.dim_location_scd2 dls 
	on ft.pickup_location_key = dls.location_key
join dw.dim_date dd 
	on ft.pickup_date_key = dd.date_key
where dls.location_id in (4, 12, 13)
group by 1, 2, 3
order by 1,2;
```

### 6. Jakość danych
Dane wprowadzone do tabeli faktów muszą spełniać poniższe warunki:
* Data rozpoczęcia kursu musi być większa lub równa niż najmniejsza wartość w tabeli wymiaru (dw.dim_date), z wyłączeniem wiersza technicznego, którego data to 1900-01-01
* Data rozpoczęcia kursu musi być mniejsza lub równa niż największa wartość w tabeli wymiaru dw.dim_date
* Data zakończenia kursu musi być późniejsza niż data jego rozpoczęcia
* Długość trasy wykonanej w ramach kursu nie może być mniejsza lub równa 0 i większa niż 100 mil
* Należność za wykonany kurs musi być większa lub równa 0

	```
  date(yt.tpep_pickup_datetime) >= (select min(full_date) from dw.dim_date where date_key <> -1)
	and date(yt.tpep_pickup_datetime) <= (select MAX(full_date) from dw.dim_date)
	and yt.tpep_dropoff_datetime > yt.tpep_pickup_datetime
	and yt.trip_distance > 0 AND yt.trip_distance <= 100
	and yt.fare_amount >= 0
  ```
Powyższe warunku odrzuciły 737 247 unikalnych kursów, w tym kursy, które naruszały kilka warunków jednocześnie.

### 9. Znane ograniczenia

* Jeśli w taxi_zones_v3 zniknie jakaś strefa, ta logika zostawi ją jako aktualną, bez zamknięcia wersji. Jest to świadome uproszczenie.
* Jeśli trasa rozpocznie się 31.12, ale zakonczy 1.01. Cały kurs nie zostanie wprowadzony do tabeli faktów, ponieważ nie będzie mogła zostać dołączona data z wymiaru 2027-01-01, ponieważ nie istnieje.
